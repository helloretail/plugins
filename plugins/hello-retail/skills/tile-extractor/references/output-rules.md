# Output rules — full text

The 13 rules of `../SKILL.md` → OUTPUT RULES, with the reasons and the field cases behind each.
Read this once per build, before workflow step 8. The short form in `SKILL.md` is binding on its
own; this file explains it and settles the edge cases.

1. **Always deliver both HTML (Liquid) and JavaScript** — never one without the other

2. **Never write CSS** — the site's existing stylesheet applies; adding CSS creates conflicts, and re-creating the native look with CSS is the habit this skill exists to prevent. Anything the tile needs from CSS that the site stylesheet will not deliver inside Hello Retail (hover-only elements, ancestor-scoped rules, alignment) is **reported** to the calling shell skill under `PARENT HOOKS`, `ALIGNMENT` and `SHELL CSS NOTES` (see RESPONSE FORMAT in `SKILL.md`) — the shell writes the CSS, in its own styles field, scoped to its own root.
   - **The one exception — shops whose CSS is not global (CSS-in-JS: MUI/Emotion, styled-components).** Their styles are injected per page and per rendered state, so the tile brings no styling with it wherever the overlay opens (verified: same tile rendered differently on a category page vs a PDP). Prove it first with the two checks in `centra.md` — injected style tags on the page, and the tile's rules missing when the same markup is harnessed on a second page type; fail either and it is a classic theme with no CSS. Then, in this order: (1) put an OPEN QUESTION to the operator — can the customer make the tile CSS global, e.g. extract the card styles into a plain stylesheet? That fixes every surface at once. (2) Only if the answer is no, return a `CSS BLOCK` that is a **copy of the customer's own rules** — the actual declarations from their style tags and sheets that match the tile's classes, rescoped under the Hello Retail root — never a stylesheet reconstructed from computed styles, never invented values. Say in SHELL CSS NOTES which rules were copied and from where.

3. **Never add comments** — no `{% comment %}`, no `{# #}`, no `/* */` anywhere in the output code

4. **Never hardcode currency** — always use `{{ product.currency | currencySymbol }}` (or the equivalent one-shot `| priceWithCurrency: product.currency` — see the Price section of `liquid-rules.md`)

5. **Never miss the form `action` attribute** — every ATC `<form>` must have `action="..."`

6. **Never skip or omit any tile element** — if feed data for an element is missing, use a static fallback value and call it out in your response text (not in the code)
   - **Exception — when the fallback would actively mislead, omit with operator approval.** A static fallback must be *harmless*. If the only available data makes the element behave wrongly (e.g. the native hover-image is a lifestyle photo but the feed's `altImage` is a *different color's* packshot — hovering would show the wrong product; or `imgUrl` as hover-image causes a contain→cover crop-jump native tiles don't have), propose omitting the element until the feed carries the right field, get the operator's sign-off, and flag it in MISSING DATA. Wrong behavior is worse than an absent nicety.
   - **Exception — platform-unsupported controls are left out by design, no approval needed.** Hello Retail does not support wishlist / favourite buttons on **Viskan / Streamline**: drop the native `.CMS-ArticleFavorite-icon` star from the tile (every native `ListArticle` carries one) and state the omission in your response text. QA grades its absence ACCEPTED, not as a missing element. → `${CLAUDE_PLUGIN_ROOT}/docs/wiki/platforms/viskan-streamline/README.md`

7. **If confused about an element's data source, say so in your response** — still include the element with your best guess or a static fallback; never silently drop it

8. **URL attributes stripped during extraction MUST be restored in the Liquid output** — `src`, `href`, `data-image`, `srcset`, `data-src`, and any other URL-bearing attribute are stripped from JS extraction snippets only to avoid browser tool blocks. They are NOT optional in the final template. Every such attribute must appear in the Liquid output populated with the matching HR feed field (e.g. `src="{{ product.imgUrl }}"`, `href="{{ product.url }}"`, `data-image="{{ product.imgUrl }}"`). If no feed field maps to it, use the best available fallback and flag it in your response text — never leave the attribute absent from the rendered HTML.
   - **Images: the feed has one `imgUrl`, so every image URL candidate binds to `{{ product.imgUrl }}`** — the `<img>`'s `src`, `srcset` and `data-src`, **and every `<source>` of a `<picture>`** (`srcset`, `data-srcset`, per format or media query). A `srcset` with one candidate is valid. Keep the `<picture>` and its `<source>` elements exactly as they are: browsers pick a source by declared format support and then decode whatever file arrives, so a source declared WebP that points at the feed's JPEG still renders — and a `<source>` left with the customer's URL wins over the `<img>` and shows the wrong product. Never rewrite the URL per platform (`_400x`, `?width=`) — the team's rule is to fix sizing in the feed, not in the template. When the native tile serves several sizes, add an OPEN QUESTION: can the customer supply sized images in the feed? Until then one URL fills every slot. During the survey compare the feed image's natural width with the native tile's rendered width (`img.naturalWidth` vs `getBoundingClientRect().width × devicePixelRatio`); if the feed image is more than ~2× the rendered size, add a MISSING DATA line — *"feed images are full-size (N px for a M px tile) — fix in the feed or ask the customer for sized images"*. Keep `loading="lazy"`, `sizes`, `media`, `type` and `width`/`height` exactly as the native tile has them (Rule 10).

9. **Never change element types** — the output must use the exact same HTML tags as the native tile. A native `<button>` stays a `<button>` with all its original attributes; a native `<a>` stays an `<a>`; a native `<object>` stays an `<object>`. Only attribute *values* that contain dynamic data (URLs, prices, IDs) are replaced with Liquid tags — the attribute *names* and element *types* are never touched. The customer's CSS and JS are bound to specific element types and selectors; changing a `<button>` to an `<a>` silently breaks hover styles, click handlers, and any JS that queries by tag name. **Custom elements too:** `<product-form>`, `<quick-add-modal>`, `<modal-opener>`, an element with `is="custom-button"` — copy them and their `is=` attributes exactly. The browser's custom-element registry upgrades them the moment they are inserted, wherever that is, so the shop's own component code runs inside Hello Retail without any binding from us; replacing one with a plain `<div>` or `<form>` throws that away. List the tag names under PLATFORM so the shell knows what already works before it writes any JavaScript.

10. **Never remove or modify attributes — preserve EVERY `id`, `class`, inline `style`, and attribute verbatim, no matter what.** Every attribute present on the native element must appear on the same element in the Liquid output, byte-for-byte, with only its *dynamic values* swapped for Liquid tags (URLs, prices, IDs). This is absolute:
    - **`class`** — keep the **entire** class list, every token, in the original order. Do **not** drop, dedupe, "clean up", or rename any class — including classes that look like runtime/JS artifacts (`lazyloaded`, `lazyautosizes`, `lazyloading`, `is-loaded`, `loaded`, `active`, `swiper-slide-visible`, `js-*`, hashed/utility classes). The customer's CSS **and** JS are bound to these exact tokens; a "harmless-looking" class is often load-bearing. Real example: dropping `lazyloaded`/`lazyautosizes` interfered with the theme's lazysizes image styling, and **a static `getComputedStyle` opacity probe is NOT reliable for deciding a class is dead** — verify in the live overlay, and when unsure, **keep the class.**
    - **`id`** — keep it; if it embeds a dynamic value, parameterize that value (e.g. `id="rating-result_{{ product.extraData.itemNumber }}"`), never delete the attribute.
    - **inline `style=""`** — keep the whole declaration verbatim (ratio-box `padding-bottom`, aspect hacks, color vars, etc.); only swap dynamic values (e.g. `background-image:url(...)`).
      - **Exception — framework loading-state styles and classes are normalized to the settled state.** Lazy/reveal components (lazysizes, React reveal wrappers) render images with `style="opacity:0;visibility:hidden"` and flip them on load via JS that never runs in HR — copied verbatim, the images stay invisible forever. Emit the *loaded* state instead (`opacity: 1`, drop `visibility:hidden`; keep any transition), and flag the change in your response. The same goes for the few **classes** that mean "not loaded yet" or "not scrolled into view yet": `lazyload` becomes `lazyloaded`; `scroll-trigger--offscreen` (Shopify Dawn/Horizon entrance animation) and `x-cloak` (Alpine) are dropped; `aos-animate` is added next to `aos-init`. Only that list — every other class stays. The hidden-state scan in `survey-snippets.md` finds stylesheet rules keyed on a tile class that set `opacity: 0`, `visibility: hidden` or a transform; anything it finds outside the list goes under SHELL CSS NOTES for the shell, never a CSS patch from you.
    - **all other attributes** — `data-*`, `tabindex`, `role`, `aria-*`, `fetchpriority`, `loading`, `width`/`height`, `data-mage-init`, `data-bind`, `srcset`, `sizes`, etc. — preserved exactly.
    - **Never remove a `style` attribute** — not even if it only contains `order:`.
    - The **only** things ever stripped from the output are (this is the complete list — the cheatsheet repeats it):
      - **Attributes the site did not author.** Browser extensions and security tools stamp the DOM they scan — Bitdefender's `bis_skin_checked="1"`, `bis_size`, `bis_id`, `bis_register`; Grammarly's `data-gramm*` / `data-gr-*`; password managers' `data-lastpass-*` / `data-1p-*` / `data-dashlane-*`; Dark Reader's `data-darkreader-*`. Provenance decides, never familiarity: the capture snippet (`survey-snippets.md` → TILE INSPECTION) removes the known families plus any attribute that appears with a constant value on nearly every element of the page, and reports what it removed — list that under ASSUMPTIONS. Every attribute the site did author stays however odd it looks: Vue `data-v-*`, Alpine `x-data`, Magento `data-mage-init`, Shopware `data-product-information`, theme-JS `aria-*`. Playwright sessions run without extensions, so the list is normally empty there; it matters on the Claude in Chrome fallback and for pasted HTML, where you apply the same denylist by hand.
      - **On the outermost tile element only — every class or inline declaration whose only job is column width or position.** The shell's skeleton owns the tile width, never the customer's root class (Rule 14). That covers grid and column classes (`col-*`, `row-*`, `grid__item`, `cms-listing-col`), per-position classes (`first`, `last`, `odd`, `even`), width utilities (`w-1/4`, `span3`) and inline `order:`, `flex-basis` and `grid-column` declarations (`style="order: 2;"` → remove the attribute entirely; `style="order: 2; background:red;"` → `style="background:red;"`). Remove such a class even when it also styles the card; if the visual check then shows the card broke, report it under OPEN QUESTIONS for the operator. **This exception applies strictly to the single root tile element — every nested element inside the tile is fully untouched, including all their `style` attributes and class lists.**
      - Shopify `section-id` / `data-section-id` values — page-specific, not in the feed; omit the attribute (`shopify.md`).
      - Framework loading-state inline styles, normalized to the loaded state as described above (a value edit, not a removal).
    - Nothing else is ever dropped — if you think an attribute/class is unnecessary, keep it anyway and (if truly noteworthy) mention it in your response text; never silently delete it.

11. **Never forget HR cart tracking on the add-to-cart button** — every button (or element) that adds a product to the cart MUST carry the HR click-tracking attribute:

    ```liquid
    onclick="hrq.push(['trackClick','{{ product.trackingCode }}'])"
    ```

    Without it, cart additions from HR-rendered tiles are not attributed to Hello Retail. This applies to every ATC pattern — plain `<form action>` submit buttons, AJAX ATC buttons, and quick-add/variant-picker buttons. If the native button already has an `onclick`, prepend the `hrq.push` call to the existing handler code rather than replacing it (e.g. `onclick="hrq.push(['trackClick','{{ product.trackingCode }}']); originalHandler()"`) — never drop the native handler (Output Rule #10).

    **And ONLY on add-to-cart actions.** Never add `trackClick` to CTAs that navigate instead of adding to cart — variant CTAs ("SE VARIANTER" / "Choose variant" links to the PDP), view CTAs ("Se mer" / "View product"), sold-out CTAs, or the tile/image/title links themselves. Hello Retail attributes those clicks through its own link handling (Search: `fix_links`; Recom: the platform's link tracking — the `#aw_source=` fragment is only visible to logged-in staff); a duplicate `trackClick` there is wrong, not extra-safe. (Scope confirmed by the QA team, 2026-07.)

12. **Tile content alignment must match the native tile** — during the survey, read the native tile's computed `text-align` (title, price, description — see `survey-snippets.md` → TILE CONTENT ALIGNMENT) and report it as an **ALIGNMENT** line for the calling shell skill. The HR Search/Recom shells set `text-align: center` at the overlay/cell level (`.hr-overlay-search`, `.hr-search-overlay-product`, `.hr-product`), and most native tiles rely on the *inherited default* (`start`) rather than setting their own — so a byte-perfect tile silently renders **centered** inside HR while the storefront shows it **left-aligned**. This skill never outputs CSS (Output Rule #2), so the compensation lives in the shell's tile-fill rule; your job is to detect and report the native value, never to assume it.

13. **Keep every control the native tile has** — quick view, notify-me, compare, wishlist, size pickers. They stay in the markup verbatim (Rule 10); whether they get *wired* is the shell skill's decision. Only the documented platform exception (Viskan wishlist, Rule 6) removes a control. List each control and what drives it natively under `SHELL CSS NOTES` / `PLATFORM` so the shell can bind it.

14. **The tile root is the per-product card, never the grid cell around it — and the shell owns the width.** Category grids wrap each card in a per-position cell (`li.grid__item`, `div.cms-listing-col`, `div.js-product.col-*`); the Search cell `.hr-search-overlay-product`, the recom `.hr-product` and the Pages item wrapper are already that cell. Copying the customer's cell as well nests a cell inside a cell: double gutters, width rules on the wrong element, an `<li>` bullet. So:
    - **Decide the root with the ancestor-chain probe** (`survey-snippets.md` → TILE INSPECTION, step 4). Walking upward, the first element that carries card chrome (border, background, shadow) or that holds the whole card as its only child is the root; a level above it that sits directly in a `display: grid` / `flex` container, has many siblings and no chrome of its own, is the customer's cell.
    - **Drop the cell.** Classes on it that the tile's CSS needs are reported under PARENT HOOKS as *cell-level*, so the shell can mirror them onto its own cell; never reproduce the cell as a wrapper.
    - **Card and cell are one element** on some platforms (WooCommerce `li.product`, Lightspeed `li.data-product`): keep that element as the root and apply the width strip of Rule 10 to it.
    - **An `<li>` root stays an `<li>`** — the customer's CSS and JS match on the tag — and gets `style="list-style-type:none;"` added (merged into an existing `style` attribute), because the shell's container is a `<div>`, not a `<ul>`. This is a sanctioned addition, not a rewrite.
    - **Width belongs to the shell.** Never keep, add or restate a width on the root; the shell's tile-fill rule sizes it. The one thing you report is the native rendered width (SHELL CSS NOTES → tile root), which the shell uses for `product_tile_width`.

15. **Nothing of Hello Retail inside the tile.** The tile body carries no `hr-*` class, no Hello Retail form and no Hello Retail wrapper, and it replaces the base design's default tile element wholesale — in Search the customer's root takes the place of `<a class="hr-search-overlay-product-link">`; in Recom and Pages it goes inside the shell's own cell, which stays the shell's. Never keep the default tile's skeleton and style it to look like the customer's card, never wrap the customer's markup in a Hello Retail element, and never substitute a Hello Retail form for the shop's own add-to-cart markup (the older Shopify `.hr-form` option is retired — copy the shop's form, Approach B in `shopify.md`). The only Hello Retail addition inside the tile is the tracking call of Rule 11. Parity is reached by copying markup and restoring reach (PARENT HOOKS), never by CSS that re-creates the native look on Hello Retail or customer classes; a difference the visual check shows is a markup deviation to fix or a shell-side rule to report, not a property to set back.

16. **Fixed texts are copied as they appear on the surveyed page, in its language.** "Add to cart", "Sold out", "From", unit labels, delivery texts: take the exact words from the page you surveyed — never translate by hand, never take them from a list. What differs per target surface: **Search and Pages** keep the text as it is (one design per domain and language; when the design is copied to another market, the copy gets its translations). **Recom** designs are reused across domains, so each fixed text becomes a dashboard input like the headline — `{% input add_to_cart_label %}` in place of the words, the native value recorded under TEXT INPUTS so the operator can fill it per domain (`{% input %}` has no default-value syntax; the field stays a dashboard value). Name inputs in snake_case after their role, not after the current wording. Worked example: `liquid-rules.md` → Fixed texts.
