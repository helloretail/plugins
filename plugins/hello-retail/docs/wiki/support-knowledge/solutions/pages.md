## Nothing renders where the category page should be

**Likely cause.** The Hello Retail script only renders a page when it finds a div whose id is
exactly `helloretail-category-page-{key}` for an active page, with a valid `data-filters`
attribute. Rule out the script first — see [script not loading](../script-not-loading.md).

**Fix.**

1. Copy the snippet from the page's **HTML & Page Key** section and place it in the `<body>`
   where the listing should render:

   ```html
   <div id="helloretail-category-page-{key}" data-filters='{ "hierarchies": ["Shoes", "Men"] }'></div>
   ```

2. Check the page is published, not only saved as a draft.
3. Check `data-filters` is valid JSON: `hierarchies` is a JSON array of levels, `brand` is a plain
   string.
4. The div is meant to be generated by the shop's template per category, not maintained by hand
   per page.

**Check with.** `pages_listConfigs` (key and state); on the storefront,
`document.querySelector('[id^="helloretail-category-page-"]')` and `JSON.parse()` of its
`data-filters`.

**Source:** [Client-Side Integration](https://support.helloretail.com/pages/client-side-integration/) · [How to Set Up Pages](https://support.helloretail.com/pages/how-to-set-up-pages/)

## The page renders but shows the wrong products or none

**Likely cause.** The values in `data-filters` (or in the page's **Product Conditions**) must match
the feed exactly — names, values and casing. A hierarchy is the full path of levels from the top,
not just the last category name.

**Fix.**

1. Read the real values from the feed and compare them with what the template writes into
   `data-filters`.
2. Write the hierarchy as the whole breadcrumb: `["Clothing", "Accessories"]`, not
   `["Accessories"]`.
3. Check the page's own **Product Conditions** in the dashboard; they also decide which products
   the page may show.

**Check with.** `productData_getFieldValues` for `hierarchies` and `brand`;
`pages_getConfigProductFilters` for the page's own conditions.

**Source:** [Client-Side Integration](https://support.helloretail.com/pages/client-side-integration/) · [How to Set Up Pages](https://support.helloretail.com/pages/how-to-set-up-pages/) · [Introduction to Pages](https://support.helloretail.com/pages/introduction-to-pages/)

## One page should combine categories or show only sale products

**Likely cause.** Not a fault: `data-filters` supports AND and OR, nested.

**Fix.**

1. Several keys in one object are ANDed: `{ "hierarchies": ["Women"], "isOnSale": true }`.
2. OR across categories:

   ```html
   <div id="helloretail-category-page-{key}" data-filters='{ "hierarchies": { "$or": [["Shoes"], ["Shirts"]] } }'></div>
   ```

3. Products in both categories: replace `$or` with `$and`. Nest freely, for example
   `{ "$or": [{ "$and": [{ "brand": "Brand A" }, { "isOnSale": true }] }, { "brand": "Brand B" }] }`.
4. Validate the JSON and test in a development theme before going live.

**Source:** [How to Set Up Pages](https://support.helloretail.com/pages/how-to-set-up-pages/) · [How to Set Up Pages for Shopify](https://support.helloretail.com/pages/how-to-set-up-pages-for-shopify/)

## Pages on Shopify collections

**Likely cause.** Shopify has no nested collections, so a category path does not exist to filter
on. Shops simulate sub-categories by linking collections or filtering a collection by tag.

**Fix.**

1. Filter on the current collection's id, written into the collection template
   (**Online Store → Themes → Edit code**), with the field `extraDataList.categoryIds` and the
   Liquid value `{{ collection.id }}`.
2. Where the theme puts the div, and collection-specific sorting, are in
   [Pages on Shopify](../../cheat-sheets/pages/shopify.md).

**Check with.** `productData_getFieldValues` for `extraDataList.categoryIds`.

**Source:** [How to Set Up Pages for Shopify](https://support.helloretail.com/pages/how-to-set-up-pages-for-shopify/)

> **May be outdated:** the article's snippet writes `data-filters` with single quotes inside a
> double-quoted attribute, which is not valid JSON; the client-side guide requires JSON. Write it
> as `data-filters='{"extraDataList.categoryIds": "{{ collection.id }}"}'` and test. The article
> also links an older API documentation site rather than developer.helloretail.com.

## Pages on DanDomain Classic

**Likely cause.** Not a fault — a setup question. Pages on DanDomain Classic needs the Advanced
Designer app, and the script works out the category from the shop's raw JSON view.

**Fix.**

1. Install the DanDomain Advanced Designer app.
2. Under **Indstillinger → Site**, edit the webshop and replace the existing Hello Retail script
   with the Pages-enabled snippet from the article, setting the Pages div's id in it. Save
   (**Gem**).
3. Under **Shopindstillinger → Layout**, enable **Tillad Rss / rå XML visning**.
4. Under **Design → Egne sider → ProductList**, open **Kilde** and insert the Pages div where the
   listing should render. Save.

**Source:** [How to Set Up Pages for DanDomain Classic](https://support.helloretail.com/pages/how-to-set-up-pages-for-dandomain-classic/)

> **May be outdated:** the snippet passes the placeholder to a jQuery `$()` call, so it has to be
> written as a selector (`#` plus the id), and it links an older API documentation site.

## Pin products to the top of one category page

**Likely cause.** Not a fault: per-URL overrides do this.

**Fix.**

1. On the page config, in the overrides section, click **Add** and enter the page's path or URL.
2. Add the products and drag them into order; the rest follow the page's boosts.
3. Toggle **Only Manual Products** to show nothing but the products you added.
4. A default popularity boost always applies to the rest and cannot be removed.

**Check with.** `pages_getConfigUrlOverrides`.

**Source:** [How to Set Up Pages](https://support.helloretail.com/pages/how-to-set-up-pages/) · [Introduction to Pages](https://support.helloretail.com/pages/introduction-to-pages/)

> **May be outdated:** the articles call the section **Product Overrides**; the
> [Pages](../../features/pages/pages.md) feature page records the current name, URL overrides.

## The product order looks distorted

**Likely cause.** Too many or too strong boosts on the page config.

**Fix.**

1. Keep to three or four boosts on a page; remove the rest under **Product Order & Boosts**.
2. Personalized boosts (on brand and similar fields) take up to a minute to apply after a change.
3. Boost and personalization changes on a config are drafts until published — see
   [Pages](../../features/pages/pages.md).

**Check with.** `pages_getConfig`.

**Source:** [Introduction to Pages](https://support.helloretail.com/pages/introduction-to-pages/)

## Filters or sorting are missing on the page

**Likely cause.** Filters and sorting belong to the design, not the page config, and need to be
switched on there. A field must be indexed to be filterable or sortable.

**Fix.**

1. In the Pages design, toggle **Filtering** and **Sorting** on, add the fields, and drag to
   order them.
2. If a field is not offered, index it under **Data Setup → Product Fields**.
3. API integrations only get filters and sorting back when `firstLoad` is `true`.

**Check with.** `pages_getDesign`, `dataFields_getProductFields`.

**Source:** [Introduction to Pages](https://support.helloretail.com/pages/introduction-to-pages/) · [Pages REST API](https://developer.helloretail.com/api/pages/)

## Changes to a page or design do not show for shoppers

**Likely cause.** Page configs and designs are edited as drafts; a live page keeps serving the
published version until someone publishes the draft in the dashboard.

**Fix.**

1. Publish the page config in the dashboard after editing it or its design.
2. A design edit creates drafts on every live page using it; publish each.
3. Preview through the on-site panel — see [review and testing](../../onboarding/review-and-testing.md).
4. An API integration can fetch a draft version by sending its `id`.

**Check with.** `pages_listConfigs`, `pages_getConfig`.

**Source:** [Pages JavaScript SDK](https://developer.helloretail.com/sdk/pages/javascript_sdk/) · [Pages REST API](https://developer.helloretail.com/api/pages/)

## The API request fails naming a missing field

**Likely cause.** The page config has a product filter of type INPUT, whose value the caller must
supply; the request does not contain it.

**Fix.**

1. Send a value for every INPUT filter in `params`, keyed by the filter's field name.
2. On a client-side integration the same values come from the div's `data-filters`.

**Check with.** `pages_getConfigProductFilters` (value type `INPUT`); `apiLog_getEntries` for the
failing request.

**Source:** [Pages REST API](https://developer.helloretail.com/api/pages/)

## Base filters sent through the API seem to be ignored

**Likely cause.** A field name in `params.filters` that is not the feed's field name — the SDK
examples write `hierarchy` where the feed field is `hierarchies`.

**Fix.**

1. Use the field names the feed has: `params: { "filters": { "hierarchies": ["Women", "Shoes"] } }`.
2. The same AND / OR syntax as `data-filters` applies.

**Check with.** `apiLog_setLogging` then `apiLog_getEntries` to see the body the shop sends.

**Source:** [Pages REST API](https://developer.helloretail.com/api/pages/) · [Pages JavaScript SDK](https://developer.helloretail.com/sdk/pages/javascript_sdk/)

> **May be outdated:** the JavaScript SDK page's examples use `hierarchy` (singular); the REST API
> page and the support articles use `hierarchies`. The SDK page also links support articles by an
> older URL scheme.

## Server-rendered page loads but filters or paging do nothing

**Likely cause.** With the HTML response the backend renders the first load, and the returned
JavaScript runs the interaction. If that JavaScript runs before the Hello Retail script is ready,
or without its container, nothing responds. Filters also live in the URL, so the backend must read
them back on reload.

**Fix.**

1. Load the Hello Retail script on the page as usual.
2. Put the returned HTML in its own container and keep a reference to it; inject the returned CSS.
3. Run the returned JavaScript only once the script is ready — after its `context_ready` event; the
   article's example wraps it in `hrq.push(function(){ … })` — passing the container, the request
   data and the page key.
4. On the backend, read the filter state from the URL (the example uses an `hr-page` query
   parameter) and send it in the request so filters survive a reload.

**Source:** [API Integration (HTML Response)](https://support.helloretail.com/pages/api-integration-html-response/) · [Pages templates](https://developer.helloretail.com/guides/templates/pages/)

## Page views are missing for an API integration

**Likely cause.** Views are only tracked for a request with `firstLoad: true`, and personalization
and tracking need the visitor's id.

**Fix.**

1. Send `firstLoad: true` on the first request for a page, `false` for paging and filtering.
2. Send `trackingUserId`, read server-side from the `hello_retail_id` cookie.
3. Send the page's `url`.

**Check with.** `apiLog_getEntries` for the requests.

**Source:** [Pages REST API](https://developer.helloretail.com/api/pages/) · [Pages JavaScript SDK](https://developer.helloretail.com/sdk/pages/javascript_sdk/)

## The category page should not go blank if Hello Retail does not respond

**Likely cause.** Not a fault — a resilience question.

**Fix.**

1. Client-side: keep the platform's own listing in a hidden div; after a timeout (the example
   uses two seconds) check whether the Hello Retail container has products, and if not show the
   platform listing and hide the Hello Retail div.
2. API integration: fall back to the platform's category page when the request fails.
3. Service status is published at status.helloretail.com.

**Source:** [Client-Side Integration](https://support.helloretail.com/pages/client-side-integration/) · [API Integration (HTML Response)](https://support.helloretail.com/pages/api-integration-html-response/)

## Will Pages hurt SEO

**Likely cause.** Client-side Pages is rendered by JavaScript. Google indexes it, but in a later
rendering pass than the plain HTML, so products can appear in the index later.

**Fix.**

1. For SEO-sensitive shops use an API integration (HTML or JSON response) so the products are
   rendered server-side.
2. Third-party SEO tools must have JavaScript rendering enabled, or they report the page empty.
3. Structured data (schema.org) can be added to the shop's page as usual.

**Source:** [Pages & Search Engine Optimization](https://support.helloretail.com/pages/pages-search-engine-optimization/)

## Category navigation in a single-page app does not update the page

**Likely cause.** A single-page app changes the view without a page load; the docs point such shops
to the SPA page-tracking setup rather than the plain div integration.

**Fix.**

1. Follow the SPA page-tracking guide and [SPA page tracking](../../onboarding/spa-tracking.md).
2. For full control, load the page with the SDK's `loadPage` and render the result yourself.

**Source:** [How to Set Up Pages](https://support.helloretail.com/pages/how-to-set-up-pages/) · [Page tracking for SPA](https://developer.helloretail.com/guides/spa/page_tracking_for_spa/) · [Pages JavaScript SDK](https://developer.helloretail.com/sdk/pages/javascript_sdk/)

## Add a custom setting to a Pages design

**Likely cause.** Not a fault: the design's JavaScript and HTML tabs can declare inputs that show
in the **Simple** tab.

**Fix.**

1. In the JavaScript tab, a dropdown:

   ```js
   /* choice("Left position", "Right", "Top") */
   var filter_position = "Left position";
   ```

2. In the HTML tab, the Liquid form is a comment such as
   `{# choice ("Left position", "Right", "Top") position = "Left position" #}`.
3. Only the field types text, number, color and choice are supported.
4. The design's JavaScript runs after the page is injected and has `container`, `data` and `page`
   in scope.

**Check with.** `pages_getDesign`.

**Source:** [Pages Design Customizations](https://support.helloretail.com/pages/pages-design-customizations/) · [Pages templates](https://developer.helloretail.com/guides/templates/pages/)

## Pages Analytics numbers look odd

**Likely cause.** Pages Analytics counts in its own way: a session ends after 30 minutes without
interaction, at midnight, or on a new campaign; sessions without interaction are not counted
(except a new user's first); impressions include filter changes and paging.

**Fix.**

1. Explain the definitions before comparing with another analytics tool.
2. High click-through with low conversion points at assortment, sizes, price or availability on
   that page rather than at Pages.

**Source:** [Pages Analytics](https://support.helloretail.com/pages/pages-analytics/)
